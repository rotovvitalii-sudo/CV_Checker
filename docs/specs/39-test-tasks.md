# C14 · Тестовые: библиотека прошлых заданий и план нового вместе с агентом

**Приоритет:** Should · **Зависит от:** W5 (подготовка к собеседованию, P1 «разбор тестового»), W6 (этапы воронки), C9 (база кейсов), C3 (уведомления)
**Оценка:** ~2 дня

## Problem Statement
Тестовое задание — самый дорогой шаг воронки: 3–10 часов работы на одну компанию. Кандидат делает его в отдельной сессии Claude Code,
и за одно задание набирается много ценного: правила работы с агентом (кто решает, кто считает), скрипты подготовки данных и проверок,
шаблоны диагноза и приоритизации, допущения, вопросы компании, шпаргалка для защиты. Сейчас всё это остаётся в папке конкретного задания
вне проекта. Следующее тестовое начинается с нуля: агент не знает, как кандидат работал раньше, что сработало, на каких развилках
он менял решение. Опыт не накапливается ни у кандидата, ни у агента.

## Goals
1. Прошлые тестовые лежат в одном месте, разобранные: тип задания, этапы, решения, что сработало, что брать повторно.
2. Новое тестовое за 5 минут получает план по этапам. В плане ссылки на готовые куски из прошлых заданий и вопросы, которые стоит задать компании.
3. Само тестовое кандидат делает в обычном чате Claude Code в папке проекта. Агент в чате видит план, библиотеку и правила и не пишет с нуля то, что уже есть.
4. После каждого тестового агент дополняет общий плейбук «как делать тестовые». Каждое дополнение проходит через «Добавить» кандидата.

## Non-Goals
- **Делать тестовое в интерфейсе CV Checker.** Работа идёт в чате Claude Code. Приложение — это библиотека, план и прогресс, а не IDE.
- **Агент решает за кандидата.** Диагноз, выводы и приоритеты — за кандидатом (правило из прошлого тестового). Агент готовит данные,
  считает, проверяет логику и предлагает, что взять из библиотеки.
- **Тестовое как опыт в CV.** Это не работа в компании: в CV и письма не идёт. Навыки, которые подтверждает тестовое, предлагаются
  в базу кейсов только как факты на «Добавить» (P1).
- **Отправка решения компании.** Отправляет кандидат сам, как и всё остальное.
- **Чужие решения из интернета.** Библиотека состоит только из собственных тестовых кандидата.

## User Stories
- Как кандидат, я хочу загрузить папку прошлого тестового (путь на диске), чтобы она сохранилась в библиотеке, даже если исходную папку я потом удалю.
- Как кандидат, я хочу нажать «Разобрать» и получить разбор: что это было за задание, по каким этапам я шёл, какие решения менял и что из этого можно взять повторно.
- Как кандидат, я хочу открыть библиотеку и найти готовый кусок по типу (скрипт, шаблон, чеклист, правила для агента, модель в xlsx, шпаргалка защиты), чтобы скопировать его в новое задание.
- Как кандидат, я хочу вставить текст нового тестового (или загрузить файлы задания) и получить план по этапам: что оценивают, что сдавать,
  сколько времени на этап, что делаю я и что агент, какие куски брать из библиотеки, какие вопросы задать компании.
- Как кандидат, я хочу открыть чат Claude Code в папке проекта, сказать «делаем тестовое <название>», и чтобы агент сам прочёл план, плейбук и библиотеку.
- Как кандидат, я хочу видеть в приложении прогресс по этапам и срок сдачи, а на странице заявки — ссылку на тестовое.
- Как кандидат, я хочу после сдачи записать результат (прошёл / не прошёл / нет ответа) и фидбек компании, чтобы разбор учитывал, что сработало на самом деле.
- *Крайний случай:* в папке прошлого тестового есть `.venv`, `node_modules`, `.git` или копия папки для загрузки на диск → при импорте они исключаются или снимаются галочкой, большие файлы показываются с размером.
- *Крайний случай:* новое тестовое не похоже ни на одно прошлое → план строится по общему плейбуку, без ссылок на библиотеку, с пометкой «новый тип задания».
- *Крайний случай:* в задании данные компании под NDA → они лежат только локально и в приватном бэкапе, в публичный репозиторий и в промпты других задач не попадают.

## Requirements
### P0
- **P0-1. Хранение:** `test-tasks/` в корне проекта, личное (в `.gitignore`, бэкапится `backup-data.sh`).
  - `test-tasks/<slug>/meta.json` — компания, роль, заявка (`vacancy`), тип задания, даты (получено / срок / сдано), часы, результат (`passed` / `failed` / `no_reply` / `pending`), фидбек компании, `source` (откуда импортировано).
  - `test-tasks/<slug>/task.md` — текст задания как есть; файлы задания лежат в `brief/`.
  - `test-tasks/<slug>/work/` — рабочая папка (для импортированного — копия исходной папки).
  - `test-tasks/<slug>/debrief.md` — разбор (P0-4); `plan.json` / `plan.md` — план (P0-6).
  - `test-tasks/PLAYBOOK.md` — общий плейбук: как кандидат делает тестовые (этапы, правила работы с агентом, проверки перед сдачей, защита).
  - `test-tasks/LIBRARY.json` — реестр повторно используемых кусков (P0-5), `LIBRARY.md` генерируется из него для чтения агентом.
- **P0-2. Экран «Тестовые»** (`#/tests`, вкладка в шапке). Список заданий: компания, роль, тип, статус (план / в работе / сдано / результат),
  срок, связь с заявкой. Внутри задания — задание, план с прогрессом, разбор, файлы. Отдельные вкладки «Библиотека» и «Плейбук».
- **P0-3. Импорт прошлого тестового:** «Добавить прошлое» → путь к папке → сервер показывает дерево с размерами.
  По умолчанию исключены `.venv`, `venv`, `node_modules`, `.git`, `__pycache__`, `.DS_Store`, сборка (`.next`, `.turbo`, `.vercel`, `coverage`), файлы больше 25 МБ; любую папку можно снять галочкой.
  **Секреты не копируются никогда:** `.env`, `.env.local` и т.п. (кроме `.env.example`), `.mcp.json`.
  Дальше «Импортировать» → копия в `test-tasks/<slug>/work/`, `meta.json` с `source`. Текст задания сервер ищет в `CLAUDE.md` / `README.md`
  папки и предлагает кандидату подтвердить; если не нашёл — вставляешь сам.
- **P0-4. «Разобрать»** — скил `test-debrief` (Sonnet, агент с чтением файлов работает только в папке задания, ≈ $0.5–1, 3–5 мин). Пишет `debrief.md`:
  - тип задания (бизнес-кейс / анализ данных / продуктовый разбор / стратегия / дизайн процесса / другое) и что оценивали;
  - этапы, как они реально шли (по README, заметкам, порядку скриптов), с примерным временем;
  - развилки: где решение менялось и почему;
  - что сработало и что повторить, что не сработало (с учётом результата и фидбека, если есть);
  - куски для библиотеки (P0-5) — кандидаты, а не сразу записи;
  - предложения в плейбук — короткие правила со ссылкой на место в задании.
  Каждое утверждение разбора — со ссылкой на файл задания; из головы агент ничего не добавляет.
- **P0-5. Библиотека:** кусок — `{id, title, type, path, from (slug задания), what, inputs, adapt (что поменять под новое задание), outcome (результат того задания)}`.
  Типы: `agent-rules` (правила для агента, `CLAUDE.md`), `script`, `template`, `checklist`, `model` (xlsx и расчёт), `defense` (шпаргалка защиты, вопросы к компании).
  Кандидаты из разбора появляются с кнопками «Добавить» / «Пропустить» / правка `what` и `adapt`. Файлы не копируются: путь указывает внутрь `work/` своего задания.
  Поиск по тексту и фильтр по типу; у куска — просмотр файла и «Скопировать в задание…».
- **P0-6. Новое тестовое:** «Новое тестовое» → текст задания (вставить) и файлы (pdf, xlsx, docx, csv → `brief/`), заявка, срок сдачи.
  «Составить план» — задача `testplan`, **Opus, один ход без инструментов**, контекст кладёт сервер: задание, извлечённый текст файлов (`scorer/cv_text.py` для pdf / docx,
  для таблиц — список листов и колонок), разбор вакансии (боль, минимум), плейбук, `LIBRARY.md`, разборы 1–2 самых похожих прошлых заданий (по типу и словам). Выход — `plan.json` / `plan.md`:
  - что на самом деле оценивают и что сдавать (формат, объём, срок, критерии из текста задания);
  - этапы (4–8): цель, результат этапа, примерное время, кто делает что («решаешь ты» / «делает агент»), куски из библиотеки (`id`, только из реестра), точка проверки;
  - вопросы компании до старта — только те, что меняют выводы (не больше 3);
  - риски и ловушки по прошлым разборам; бюджет времени против заявленного в задании.
  Проверка сервером: `id` кусков существуют, сумма времени этапов не больше бюджета задания × 1.3, у каждого этапа есть результат. Не прошло — одна повторная попытка.
- **P0-7. Работа в чате — скил `test-task`** (`.claude/skills/test-task/`). Кандидат говорит в Claude Code «делаем тестовое <название>», скил:
  - читает `meta.json`, `plan.json`, `PLAYBOOK.md`, `LIBRARY.md`;
  - копирует выбранные куски в `work/` (отмечает в плане, что взято);
  - работает по этапам с правилами плейбука: перед нетривиальным расчётом — метод и «ок», у каждой цифры — откуда она, допущения — в `work/notes/assumptions.md`;
  - отмечает этап в `plan.json` (`todo` → `doing` → `done`), приложение показывает прогресс без перезагрузки.
  При создании задания сервер кладёт в `work/CLAUDE.md` правила из куска `agent-rules` последнего успешного задания (или из плейбука) — так работает и чат, открытый прямо в `work/`.
  На экране задания — кнопка «Скопировать команду для чата» с текстом для Claude Code.
- **P0-8. Связи:**
  - на странице заявки — блок «Тестовое»: этап N из M, срок, ссылка;
  - уведомление (C3) за день до срока;
  - после «Сдал» — поля результата и фидбека, они появляются, когда компания ответит;
  - разбор (P0-4) можно перезапустить, когда пришёл фидбек.
- ✅ Импорт первого тестового: дерево без `.venv`, копия ≈ 6 МБ, задание найдено в `CLAUDE.md`. Разбор: этапы, развилки и не меньше 6 кусков, у каждого — путь
  к существующему файлу. Новое тестовое: план ссылается только на существующие куски, вопросов компании не больше 3. Скил в чате находит задание
  по названию и отмечает этап, и это видно в приложении.

### P1
- **Разбор тестового для собеседования** (закрывает P1 из W5): по `debrief.md` и шпаргалке защиты — блок «Защита тестового» в «Собеседовании»:
  «на какие цифры нападут», ответы, развилки решений. В тренажёре W5 — вопросы по тестовому.
- **Факты в базу кейсов:** навыки, которые тестовое показало (модель unit economics, A/B-размер выборки), предлагаются в «Предложено добавить» (C9) с пометкой «тестовое, не работа».
- **Этап воронки «Тестовое»** в W6 между hiring manager и финалом; в «Статистике» — доля перехода после тестового и часы на тестовое против исхода.
- **Обновление плейбука по итогам:** после результата `passed` / `failed` — «Что поменять в плейбуке?» с учётом всех разборов (Sonnet, по кнопке).
- **Проверка перед сдачей:** чеклист из плейбука по `work/` (все ли части задания закрыты, у цифр есть источник, объём в лимите) — один ход Haiku.

### P2
- Сравнение похожих тестовых между собой: что повторяется у компаний одного типа.
- Шаблон «рабочего файла» xlsx, который собирается скриптом из библиотеки под новое задание.

## Success Metrics
- **Leading:** у каждого нового тестового есть план до начала работы; в ≥ 70% планов есть хотя бы 2 куска из библиотеки, и их реально скопировали в `work/`.
- **Quality:** 0 ссылок плана на несуществующие куски; ≤ 1 из 5 пунктов разбора кандидат правит как «не так понял».
- **Lagging:** время на тестовое того же типа падает (часы в `meta.json`); доля тестовых, после которых зовут дальше, растёт.
- **Цена:** разбор ≈ $0.5–1 один раз на задание, план ≈ $0.2–0.4.

## Решения (2026-11-02)
- Импорт — **копия папки целиком** (без `.venv`, `node_modules`, `.git` и т.п.); исходная папка библиотеке больше не нужна.
- Новые тестовые — **внутри CV Checker**, `test-tasks/<slug>/work/`: один чат Claude Code видит и задание, и библиотеку.
- Данные компаний из тестовых — **в приватный бэкап** вместе с остальным `test-tasks/`.
- План — **Opus** (задача `testplan`, меняется на экране «Агент»).
