# Разбор тестового (C14)

Цель — чтобы следующее тестовое начиналось не с нуля: агент и кандидат знают, как он работал, на каких развилках менял решение
и какие готовые куски можно взять. Разбор — это материал для библиотеки и плейбука, а не оценка работы.

## Правила
1. **Только из папки задания.** Читай `test-tasks/<slug>/task.md` и `test-tasks/<slug>/work/`. Каждое утверждение разбора —
   со ссылкой на файл (`work/notes/assumptions.md`), можно с разделом. Чего нет в файлах — не пиши; не знаешь — «не видно по файлам».
2. **Кандидат решает, агент помогает.** Разбор описывает решения кандидата его словами (из README, заметок, итогового ответа), не переоценивает их.
3. **Сначала обзор, потом глубина.** Начни с `README.md`, `CLAUDE.md`, списка файлов (Glob `test-tasks/<slug>/work/**`). Итоговый ответ и заметки
   читай целиком, скрипты — первые 40 строк и docstring, большие таблицы и бинарные файлы не открывай (достаточно имени и места в процессе).
   Не читай `.venv`, `node_modules`, кэш.
4. **Результат учитывай честно.** Если в задаче сказано `result: passed / failed` или есть фидбек компании — «что сработало / не сработало»
   опирай на него. Если результата нет — пиши «результат неизвестен», без догадок.
5. **Без личного и чужого.** Не переписывай в разбор данные компании (цифры data pack, внутренние метрики) — только как они использовались.
   В правила плейбука не попадают названия компаний и цифры — правило должно работать на любом задании.

## Кандидаты в библиотеку
Повторно используемый кусок — файл (или папка), который можно взять в следующее тестовое и поменять под него за минуты, а не часы.
Типы: `agent-rules` (правила для агента, `CLAUDE.md`), `script` (подготовка и проверка данных, расчёты, сборка рабочего файла, графики),
`template` (структура ответа, диагноз на одну страницу, длинный список рычагов, допущения, вопросы компании), `checklist`,
`model` (рабочий xlsx, модель расчёта), `defense` (шпаргалка защиты, вопросы к компании и интервьюеру).
- `path` — **существующий** путь относительно `work/` (сервер отбрасывает несуществующие). Предпочитай общий кусок частному:
  скрипт выгрузки вкладок в CSV — да, скрипт расчёта конкретной метрики этой компании — только если метод переносится.
- `what` — что делает (одна фраза), `inputs` — что нужно на входе, `adapt` — что поменять под новое задание (имена колонок, пути, разделы).
- 5–12 кусков; не дублируй то, что уже есть в `test-tasks/LIBRARY.md`.

## Правила в плейбук
Короткие правила (одна фраза, повелительное наклонение), которые сработали или которых не хватило: как шли этапы, как работали с агентом,
что проверить перед сдачей, как готовиться к защите, какие ловушки встретились. Раздел — один из: «Правила работы с агентом», «Этапы»,
«Перед сдачей», «Защита», «Ловушки». `ref` — файл задания, откуда правило. 3–10 правил; то, что уже есть в `test-tasks/PLAYBOOK.md`, не повторяй.

## Выход
`test-tasks/<slug>/debrief.md` (по-русски, 1–2 страницы):
```
# Разбор: <роль> — <компания>
Тип: … · Что оценивали: … · Время: ~N ч (откуда видно) · Результат: …
## Задание коротко
## Как шла работа            — этапы по порядку: что делал, результат этапа, файлы
## Развилки                  — где решение менялось и почему (со ссылкой)
## Что сработало
## Что не сработало / чего не хватило
## Что брать в следующее тестовое   — список кусков с путями
```
`test-tasks/<slug>/debrief.json`:
```json
{"type": "business-case|data|product|strategy|process|other", "evaluates": ["…"], "hours": 0,
 "stages": [{"title": "…", "what": "…", "result": "…", "files": ["work/…"]}],
 "forks": [{"what": "…", "why": "…", "ref": "work/…"}],
 "worked": ["…"], "didnt": ["…"],
 "library": [{"title": "…", "type": "script", "path": "analysis/00_export_csv.py", "what": "…", "inputs": "…", "adapt": "…"}],
 "playbook": [{"rule": "…", "section": "Ловушки", "ref": "work/…"}]}
```
`hours` — 0, если по файлам не видно. Больше ничего не меняй: ни `meta.json`, ни библиотеку, ни плейбук.
